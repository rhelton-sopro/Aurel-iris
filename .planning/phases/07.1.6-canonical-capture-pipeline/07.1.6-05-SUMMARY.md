## Decisions Implemented

### D-01 — fire-and-forget never blocks finalize

`finalizeReadingAction` (apps/web/app/actions/readings.ts L127-150) wraps o fetch a `/api/capture/canonicalize` em `try { ... } catch (err) { console.error(...) }`. Falhas (network throw, 500, 502) NÃO propagam ao terapeuta — apenas log estruturado em stderr. O Modal trigger no L162 segue rodando, e process/route.ts cai em `storage_path` para qualquer imagem onde `canonical_storage_path` ainda esteja `NULL` (porque o canonicalize falhou ou foi parcialmente fallback per-imagem).

Pattern empírico-validated via 3 testes do contract suite (`returns soft-warn on 502 / 4xx / network throw` — todos passam pós-Task 1 porque o canonical fetch também é mockado, retorna 502, e seu error é silenciosamente absorvido).

### D-04 — CANONICAL_CAPTURE_ENABLED env-flag

`finalizeReadingAction` NÃO re-checa a env var — apenas dispara o POST. O orchestrator `canonicalizeReading` (Plan 03 index.ts) honra `process.env.CANONICAL_CAPTURE_ENABLED !== 'false'` na entrada: quando 'false', retorna early com 6× `canonical_status='disabled'` e `canonical_storage_path` na DB stays `NULL`. Process/route.ts então cai em `img.canonical_storage_path ?? img.storage_path` = `storage_path` para todas as 6 imagens — comportamento idêntico ao pre-07.1.6.

Kill-switch operacional: `vercel env add CANONICAL_CAPTURE_ENABLED false` + redeploy → rollback completo em 1 commit + env update sem código novo.

### Backward-compat com readings pre-07.1.6

Readings criadas antes do deploy desta fase (~10-20 readings legacy, per CONTEXT.md D-05) têm `canonical_storage_path IS NULL` para todas as imagens. O process route resolve para `storage_path` automaticamente — comportamento idêntico Phase 5. Pre-07.1.6 readings reprocessadas via Reprocessar button (05-14) usam raw paths sem fricção; founder pode opt-in pra re-canonicalizar via /admin/calibration (Plan 06 — coming).
