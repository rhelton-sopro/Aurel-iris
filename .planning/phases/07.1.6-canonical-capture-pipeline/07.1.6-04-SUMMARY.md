# Phase 07.1.6 Plan 04: POST /api/capture/canonicalize Endpoint Summary

POST endpoint wrapping `canonicalizeReading()` orchestrator (Plan 03) com auth gate + ownership check, exposto como single entry point pra finalize action (Wave 2 Plan 05) e admin Re-canonicalizar button (Wave 2 Plan 06).

## What Was Built

### `apps/web/app/api/capture/canonicalize/route.ts` (123 linhas, novo)

Single export `POST(request: NextRequest): Promise<NextResponse>` com runtime `'nodejs'` (sharp + Anthropic SDK não rodam em Edge). Fluxo de 4 estágios:

1. **Body parse + validate** (lines 53-67): try/catch JSON parse → 400 em malformed; `typeof body.readingId !== 'string' || length === 0` → 400 com `'readingId (string) required'`. Único campo lido do body (orchestrator inputs derivados server-side: `therapistId = user.id`, T-07.1.6-17 mitigation).

2. **Auth gate** (lines 69-77): `createClient()` user-session client → `supabase.auth.getUser()` → 401 `'Unauthenticated'` se `user == null` OR `authError`. Espelhado verbatim de `apps/web/app/api/readings/[id]/process/route.ts` L43-51 (Phase 5 closest analog).

3. **Ownership check** (lines 79-94): `.from('readings').select('id, therapist_id').eq('id', readingId).eq('therapist_id', user.id).single()` → 404 `'Reading not found'` em readingError OR `!reading`. RLS-enforced via user client; `.eq('therapist_id', user.id)` é defense-in-depth (T-07.1.6-16 spoofing mitigation — cross-tenant readingId tampering retorna 404 determinístico).

4. **Delegate to orchestrator** (lines 96-122): try → `await canonicalizeReading(readingId, user.id)` → 200 `{ results, metadata, status_summary: metadata.status_summary }` (status_summary é convenience copy do metadata field). catch → log via `console.error` com stack server-side, retorna 500 com `errorMessage = err.name + ': ' + err.message` (sem stack ao cliente; T-07.1.6-19 information disclosure mitigation).

### Comportamentos não-implementados (by design, NÃO são deviations)

- **NÃO dispara vision pipeline downstream** — esse trigger permanece em `apps/web/app/api/readings/[id]/process/route.ts` (Wave 2 Plan 05 atualizará process route a resolver `canonical_storage_path ?? storage_path`). Verify script asserts ausência do token `triggerVisionPipeline` no source.
- **NÃO chama `revalidatePath`** — responsabilidade do caller (finalize action ou admin client).
- **NÃO consulta `auth.users`** — MEMORY rule (`feedback_supabase_rls_no_auth_users.md`): authenticated role lacks SELECT no schema auth. `user.id` da sessão basta para ownership match.
- **NÃO re-checa env-flag CANONICAL_CAPTURE_ENABLED** — D-04 enforcement vive em `canonicalizeReading` (Plan 03 index.ts L102-126); kill-switch via `vercel env CANONICAL_CAPTURE_ENABLED=false` afeta orchestrator, endpoint passa direto.
- **NÃO faz rate-limit explícito** — auth-gated (sem unauth abuse); founder usage ≤3 readings/dia; Anthropic Tier 1 5 RPM Sonnet limit é fail-safe (429 propaga via canonicalizeReading throw → 500). Rate-limit deferred per PROJECT.md envelope (T-07.1.6-20 accepted).

## Idempotency Trace (D-05)

Quando o admin clica Re-canonicalizar:
1. `POST /api/capture/canonicalize { readingId }` → auth + ownership passa.
2. `canonicalizeReading(readingId, user.id)` re-executa 6× Sonnet bbox call (não há cache).
3. `service.storage.from('iris-captures').upload(canonical/{eye}_{angle}.jpg, buf, { upsert: true })` sobrescreve blob canonical existente.
4. `service.from('reading_images').update({ canonical_storage_path: path }).eq('reading_id', X).eq('eye', Y).eq('angle', Z)` re-écreve o mesmo path (no-op em DB).
5. `service.from('readings').update({ canonical_metadata })` re-escreve aggregate metadata.

**Originais NUNCA tocados:** `storage_path` column intocada, `originais/{eye}_{angle}.jpg` blob intocado. Pior caso: founder gasta $0.05 re-clicando — accepted per T-07.1.6-22.
