## SDK API differences encountered (vs research expectation)

The PLAN's `<interfaces>` block contains the full file content, with this directive at the end:

> If the TS SDK's actual API differs from `result.data[i].embedding`, adjust the implementation accordingly. The implementation should match whatever `voyageai@0.2.1` exposes; verify by reading the package's `.d.ts` after install if needed.

Reading `node_modules/voyageai/dist/esm/api/types/EmbedResponse.d.mts` and adjacent files revealed:

```typescript
export interface EmbedResponse {
    object?: string;
    data?: VoyageAI.EmbedResponseDataItem[];   // ← OPTIONAL
    model?: string;
    usage?: VoyageAI.EmbedResponseUsage;        // ← OPTIONAL
}
export interface EmbedResponseDataItem {
    object?: string;
    embedding?: number[];                       // ← OPTIONAL
    index?: number;
}
export interface EmbedResponseUsage {
    totalTokens?: number;                       // ← OPTIONAL
}
```

The PLAN's verbatim mapping `result.data.map((d) => d.embedding)` would fail tsc strict because both `data` and `embedding` are optional in the Fern-generated types. embed.ts uses defensive coalescing instead:

```typescript
const embeddings = (result.data ?? []).map((d) => d.embedding ?? [])
const totalTokens = result.usage?.totalTokens ?? 0
```

Tests still pass cleanly because the mock returns the canonical (non-empty) shape. This is a Rule 1 (correctness) deviation that the PLAN explicitly anticipated and authorized.

Other notes:
- TS SDK uses camelCase (`inputType`, `totalTokens`) while Python uses snake_case — matches RESEARCH expectation.
- `VoyageAIClient.embed(...)` returns `core.HttpResponsePromise<EmbedResponse>` which extends `Promise<EmbedResponse>`, so `await` works as expected.
- Built-in retry (default limit 2) is verified — the PLAN correctly notes no explicit retry layer is needed in TS (Python's `embedder.py` adds 1s/4s/16s manually because the Python SDK lacks built-in retries).
