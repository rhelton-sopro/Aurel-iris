### Task 3 — BilateralFindingsEditor + Checkbox primitive + PointerEvent polyfill (RED→GREEN)

**Component (`apps/web/components/readings/BilateralFindingsEditor.tsx`, 122 lines):**

- UI-SPEC FLAG-5: Card title `Achados bilaterais` renders unconditionally — unlike read-only `BilateralFindingsCard` which returns `null` when `!asymmetry_present`, the editor explicitly opts out so the therapist can toggle `asymmetry_present=true` if the LLM missed it.

**Checkbox UI primitive (`apps/web/components/ui/checkbox.tsx`, 37 lines):**

- Thin shadcn-style wrapper around `@base-ui/react/checkbox` (already installed via `@base-ui/react@1.4.1`).
- API: `{ checked, onCheckedChange, disabled, id }` matches base-ui Root.
- Indicator uses lucide `CheckIcon`.
- First consumer in the app — no prior Checkbox primitive existed (Rule 3 missing dependency).

**PointerEvent jsdom polyfill (`apps/web/tests/setup.ts`):**

- jsdom does NOT implement `PointerEvent`. base-ui Checkbox `onClick` handler at `node_modules/@base-ui/react/esm/checkbox/root/CheckboxRoot.js:278` constructs `new PointerEvent('click', ...)` which throws `ReferenceError: PointerEvent is not defined` inside the React dispatch loop. The error is swallowed by React's event system, but the side effect is that `onCheckedChange` silently no-ops.
- Fix: fall back to `MouseEvent` (which has the click-event subset base-ui touches — `type`, `button`, `currentTarget`). Cast via `as unknown as typeof PointerEvent`.
- Unblocks all future base-ui pointer-event component tests (other Select/Checkbox usage already worked because Select keypath uses different events).

**Test (`BilateralFindingsEditor.test.tsx`, 10 cases):**

- Card title renders even when `asymmetry_present=false` (FLAG-5 contract)
- `Sem assimetria registrada.` copy when collapsed + asymmetry=false
- `Editar` button calls `onExpand`
- Checkbox + Textarea both render when expanded + asymmetry=false (FLAG-5 contract)
- Toggling Checkbox calls `onChange` with `asymmetry_present: true`
- Typing into description calls `onChange` with the typed string
- Clearing description textarea sets `description: null`
- Existing description renders in collapsed mode when `asymmetry_present=true`
- `Salvar bloco` disabled when not dirty
- `Salvar bloco` enabled when bilateral differs from initialBilateral

## Threat Model

All Plan 07b threat register entries (T-07.4-07b-01 through T-07.4-07b-06) are mitigated or accepted as designed:

- **T-01 (system_id tampering):** Mitigated — `system_id` is read-only in the UI (display only; `data-system-id` attribute on Card root, but never bound to a form control); the 12-element enum constraint in `report-schema.ts` is enforced server-side by Plan 05's `reportV2Schema` re-validate before persist.
- **T-02 (tendency_label tampering):** Mitigated — `tendency_label` Select is bound to `TENDENCY_LABELS` enum client-side; server-side `reportV2Schema.parse` defense-in-depth enforces the enum on the persisted value.
- **T-03 (lost local state on navigation):** Accepted — same threat model as Plan 07's simple-text editors; `useTransition` + dirty count + sticky footer give visibility; persist requires explicit Save click.
- **T-04 (no console leakage):** Accepted — zero `console.log` in production code; matches Plan 06/07 pattern.
- **T-05 (1000-axes DOS):** Accepted — no client-side cap; server zod schema has no `maxItems` for `integrative_axes` (relaxed by design); founder UAT will surface if needed.
- **T-06 (description empty-string vs null):** Mitigated — `BilateralFindingsEditor` Textarea `onChange` normalizes `e.target.value === '' ? null : value`; zod schema accepts `string | null`.

No new threat surfaces introduced beyond the plan's register.
