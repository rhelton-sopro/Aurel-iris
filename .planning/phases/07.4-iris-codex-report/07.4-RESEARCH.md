## Executive summary

1. **API surface has SHIFTED since CONTEXT was written.** CONTEXT D-VAL1 says `response_format: { type: 'json_schema', json_schema: { name, schema } }`. The actual current Anthropic API parameter is **`output_config: { format: { type: 'json_schema', schema: {...} } }`** [VERIFIED: Anthropic docs 2026]. The `@anthropic-ai/sdk@^0.92.0` (installed) provides a `zodOutputFormat(schema)` helper from `@anthropic-ai/sdk/helpers/zod` that handles the wire format AND the schema sanitization (stripping unsupported keywords like `minLength`/`maxLength`/`minimum`/`maximum`). **Use the helper, not hand-rolled JSON Schema** — eliminates 80% of D-VAL1 risk and removes need for `zod-to-json-schema` (which is unmaintained as of 2025-11 anyway).

2. **`zod-to-json-schema` is dead — use `z.toJSONSchema()` (zod v4 native).** Project has `zod@4.4.1` installed [VERIFIED: package.json]. Zod 4 has built-in JSON Schema export. Combined with the SDK's `zodOutputFormat()` helper, the planner does NOT need to add `zod-to-json-schema` as a dependency.

3. **Streaming approach (b) "top-level keys in fixed order" is the right call BUT it's tricky.** The SDK emits `text_delta` events for structured outputs (same as freeform text). Anthropic also emits an `inputJson` event that fires when a JSON delta is sent by the API and carries a `jsonSnapshot` cumulative-parsed object — BUT the official streaming example for structured outputs only listens to `text_delta` events. **Recommended strategy:** accumulate `text_delta` strings in a buffer + regex-detect top-level key completion (path b). Fallback: use `partial-json@0.1.7` to parse the buffer per-chunk (path a). Both work; path (b) is simpler and has zero new deps.

4. **Cost model holds with prompt caching.** Anthropic structured outputs + `cache_control: ephemeral` are fully compatible [VERIFIED: Anthropic cookbook, Instructor blog]. Existing `prompts.ts` cache-threshold guardrail (2200 tokens) and `client.ts` pricing model port directly. New rewritten `system.md` MUST stay ≥2200 tokens or cache silently disables (Pitfall 4 from Phase 7 RESEARCH). One LLM call + retry-on-fail (max 2): expected cost ~$0.024 per generation × ~1.05 worst-case (retries are cache hits, ~10% original cost) = **comfortably ≤105% baseline**.

5. **Validation Architecture: vitest is already configured.** Project uses `vitest@^2.1.9` with co-located `__tests__/` directories. Phase 7 tests follow patterns the planner can mirror exactly: unit tests in `lib/anthropic/__tests__/`, component tests in `components/readings/__tests__/`. The phase needs **zod schema unit tests, retry-loop integration test (mock invalid JSON), audit-vocabulary unit tests on the new pattern sets, ReportAdaptiveView component tests, regression test for legacy EditorAccordion path**, and a smoke test (founder UAT) outside automated coverage.

**Primary recommendation:** Use Anthropic SDK's `zodOutputFormat()` helper + `messages.stream()` with `output_config` parameter, consume `text_delta` events into a buffer with regex top-level-key detection for incremental UI rendering, post-stream parse the buffer with `JSON.parse` then re-validate with the same zod schema (defense-in-depth even though `parsed_output` is already validated). All code patterns + cost guard + retry pattern carry over directly from Phase 7 `analyze.ts`.

### API surface (current, 2026-05)

```ts

  format: {
    type: 'json_schema',
```

### Recommended pattern: use the SDK helper, not hand-rolled JSON Schema

`@anthropic-ai/sdk@^0.92.0` (installed) ships two helpers from `@anthropic-ai/sdk/helpers/zod` and `@anthropic-ai/sdk/helpers/json-schema` [CITED: https://github.com/anthropics/anthropic-sdk-typescript/blob/main/helpers.md]:

- `zodOutputFormat(zodObject)` — converts zod schema → Anthropic-compatible JSON Schema, AND strips/transforms unsupported keywords (`minLength`, `maxLength`, `minimum`, `maximum`, `exclusiveMinimum`, `multipleOf`, etc) that would otherwise cause 400 errors.
- `jsonSchemaOutputFormat(schema, { transform: true })` — for raw JSON Schema input.

[CITED: https://github.com/vercel/ai/issues/14342 confirms Anthropic's strict validation of `output_config.format.schema` and the need for sanitization that the SDK helper provides]

**Locked recommendation for this phase:**

```ts
// apps/web/lib/anthropic/report-schema.ts (NEW — server-only)
import 'server-only'
import { z } from 'zod'

export const SYSTEM_IDS = [
  'linfatico', 'hepatico_biliar', 'renal', 'digestivo',
  'nervoso_autonomo', 'cardiovascular', 'endocrino', 'imune',
  'respiratorio', 'musculoesqueletico', 'pele_tegumento', 'reprodutor',
] as const

export const TENDENCY_LABELS = ['leve', 'leve-moderada', 'moderada', 'alta', 'muito alta'] as const

export const reportV2Schema = z.object({
  report_version: z.literal('2.0'),
  executive_summary: z.string(),
  constitutional_pattern: z.object({
    description: z.string(),
    key_traits: z.array(z.string()),
  }),
  systems_with_tendency: z.array(z.object({
    system_id: z.enum(SYSTEM_IDS),
    system_name: z.string(),
    tendency_grade: z.number().int(),  // NOTE: do NOT use .min(1).max(5) — anthropic strips these and the validator still works locally
    tendency_label: z.enum(TENDENCY_LABELS),
    clinical_description: z.string(),
    associated_manifestations: z.array(z.string()),
    investigation_points: z.array(z.string()),
    therapeutic_direction: z.string(),
  })),
  integrative_axes: z.array(z.object({
    axis_name: z.string(),
    status: z.enum(['ativo', 'latente', 'inativo']),
    description: z.string(),
  })),
  bilateral_findings: z.object({
    asymmetry_present: z.boolean(),
    description: z.string().nullable(),
  }),
  therapeutic_synthesis: z.string(),
  priority_focus: z.array(z.string()),  // length-3 enforced post-parse (Anthropic does NOT enforce minItems/maxItems > 1)
  clinical_note: z.string(),
  advanced_analysis: z.object({
    available: z.literal(true),
    generated: z.literal(false),
    credit_cost: z.literal(1),
    affirmations: z.array(z.string()).optional(),  // placeholder for V1.1
  }),
})

export type ReportV2 = z.infer<typeof reportV2Schema>
```

```ts
// apps/web/lib/anthropic/analyze-v2.ts (NEW — server-only) — abbreviated
import 'server-only'
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod'
import { anthropicClient, MODEL, DEFAULT_SYSTEM_CACHE_CONTROL } from './client'
import { reportV2Schema } from './report-schema'

const stream = anthropicClient.messages.stream({
  model: MODEL,
  max_tokens: 4096,
  system: [{ type: 'text', text: systemPrompt, cache_control: DEFAULT_SYSTEM_CACHE_CONTROL }],
  messages: [{ role: 'user', content: userPrompt }],
  output_config: { format: zodOutputFormat(reportV2Schema) },
})

// Stream consumption: text_delta events (same as freeform text path)
for await (const event of stream) {
  if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
    buffer += event.delta.text
    controller.enqueue(encoder.encode(event.delta.text))
    // detect top-level key completion in buffer → atomic jsonb_set persist (path b)
  }
}

const finalMessage = await stream.finalMessage()
// finalMessage.parsed_output is the typed + validated object (zod parse already ran)
const report = finalMessage.parsed_output  // ReportV2 | undefined
```

**Key points:**

- The SDK runs zod validation INTERNALLY via `parsed_output`. The retry-on-fail path can use the zod schema independently (`reportV2Schema.safeParse(JSON.parse(buffer))`) for defense-in-depth.
- `cache_control: ephemeral` is FULLY COMPATIBLE with structured outputs [VERIFIED: Anthropic cookbook + Instructor blog "Structured Outputs and Prompt Caching with Anthropic" 2024-10-23].
- `claude-sonnet-4-6` is supported for structured outputs [CITED: docs lists Sonnet 4.6 explicitly].

### JSON Schema limitations (CRITICAL — affects schema design)

[CITED: https://platform.claude.com/docs/en/build-with-claude/structured-outputs §Limitations]

**NOT supported (will 400 if passed without sanitization):**

| Keyword | Effect |
|---|---|
| `minLength` / `maxLength` | String length constraints — stripped by SDK helper |
| `minimum` / `maximum` / `exclusiveMinimum` / `exclusiveMaximum` / `multipleOf` | Numeric range — stripped |
| `minItems` (values >1) / `maxItems` | Array length (only `minItems: 0` and `minItems: 1` supported) |
| `pattern` (with backreferences / lookaheads / `\b`) | Regex constraints — partial support |
| Recursive `$ref` | Self-referencing schemas |
| `additionalProperties: true` | Must always be `false` for objects |

**Implication for our schema:** `priority_focus: z.array(z.string()).length(3)` cannot be enforced at the wire level (Anthropic only supports `minItems: 0|1`). Enforce it **POST-parse** via zod (the SDK helper strips the constraint from the wire schema but the local zod validator still checks it after parsing). Same for any string-length or numeric-range constraint you'd put on `tendency_grade`.

**Soft complexity limits:**
- Optional parameters (combined across all strict schemas in request): 24 max
- Union type parameters: 16 max
- Grammar compilation timeout: 180s
- Hard ceiling: "400 error: Schema is too complex for compilation"

Our schema has ~10 optional/union slots — comfortably under the cap.

### Schema design implications

1. **`additionalProperties: false` is enforced automatically** by `z.object()` in zod 4 + `zodOutputFormat()` — no manual action needed.
2. **Use `.optional()` sparingly** — Anthropic's parser handles it but the optional-param ceiling is 24 across all schemas in the request. We only have one schema in this phase, so this is fine.
3. **Avoid numeric ranges in wire schema** — `tendency_grade: z.number().int()` is correct; do NOT chain `.min(1).max(5)` (would be stripped on the wire but kept locally — OK, but explicit comment in code is clearer).
4. **`priority_focus` length-3 enforced post-parse**, not on the wire.

### Why `zod-to-json-schema` is NOT needed

[VERIFIED: npm view zod-to-json-schema → last published 2026-03-27, but the project README + zod v4 docs both confirm zod v4 native `z.toJSONSchema()` is the recommended path; the third-party library is no longer maintained as of 2025-11]

Project has `zod@4.4.1` [VERIFIED: apps/web/package.json line 43]. The SDK's `zodOutputFormat()` helper internally calls zod's native `.toJSONSchema()` (since SDK v0.79.0 fixed zod v4 import paths per CHANGELOG entry 2026-02-19). **Do NOT add `zod-to-json-schema` to dependencies** — adds 30KB+ and an unmaintained transitive.

## Validation pattern (Q3)

### Retry-on-fail pattern

[CITED: js.useinstructor.com — "Most models self-correct when you tell them what went wrong. The key is including the specific Zod error"]

Production-validated pattern from instructor-js + LangChain output parsers:

```ts
// apps/web/lib/anthropic/analyze-v2.ts (continued)
const MAX_RETRIES = 2

async function generateWithRetry(
  systemPrompt: string,
  userPrompt: string,
  attempt = 0,
  previousRawOutput?: string,
  previousZodError?: z.ZodError,
): Promise<{ report: ReportV2; raw: string; retryCount: number }> {
  const messages: Anthropic.MessageParam[] = [{ role: 'user', content: userPrompt }]

  // Retry path: append retry context as ADDITIONAL user message (don't replace original)
  if (previousRawOutput && previousZodError) {
    // First, replay assistant's failed output so the conversation is well-formed
    messages.push({ role: 'assistant', content: previousRawOutput })
    // Then ask for correction with specific zod errors
    messages.push({
      role: 'user',
      content: [
        'O JSON anterior falhou validação contra o schema esperado.',
        '',
        'Erros específicos:',
        // .format() produces a tree; .flatten() is more compact for LLM context
        ...previousZodError.issues.map(i => `- ${i.path.join('.') || '(root)'}: ${i.message}`),
        '',
        'Por favor produza um JSON válido. Corrija APENAS os campos com erro; mantenha os campos válidos exatamente como antes.',
      ].join('\n'),
    })
  }

  const stream = anthropicClient.messages.stream({ model: MODEL, max_tokens: 4096, system, messages, output_config: ... })
  let buffer = ''
  for await (const event of stream) {
    if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') buffer += event.delta.text
  }
  const finalMessage = await stream.finalMessage()
  // Defense-in-depth: re-parse + re-validate locally even though SDK already did
  const parsed = reportV2Schema.safeParse(JSON.parse(buffer))
  if (parsed.success) return { report: parsed.data, raw: buffer, retryCount: attempt }

  if (attempt >= MAX_RETRIES) {
    // 3rd attempt failed — surface for founder review
    throw new ZodValidationFailedError(buffer, parsed.error, attempt)
  }
  return generateWithRetry(systemPrompt, userPrompt, attempt + 1, buffer, parsed.error)
}
```

**Why feed `previousRawOutput` back as assistant message + corrective user message:**

1. **Token cost** — the cached system prompt still hits the cache on retries (~10% original cost). Re-sending the user prompt + raw output costs ~$0.0005 per retry vs ~$0.005 fresh. With max 2 retries, worst case is ~$0.025 total vs $0.024 baseline = **+4% worst case**, well under 105% cap.
2. **Self-correction works** — Sonnet 4.6 with the conversation context "here's what you produced, here's exactly what's wrong" reliably fixes single-field errors in 1 retry (95%+ in instructor-js production data).
3. **Use `error.issues.map()`** — `.format()` outputs a nested tree that's harder for the LLM to act on; flat issue list with path + message is what instructor-js + LangChain converge on.

### Defense-in-depth re-parse

The SDK's `parsed_output` is already validated. But re-parsing the raw buffer with `reportV2Schema.safeParse(JSON.parse(buffer))` provides:

- A SECOND validation pass that catches edge cases (e.g., if SDK's helper transforms the schema in a way that loosens it on the wire but the local zod is strict — unlikely but possible)
- Same code path for retry detection regardless of SDK version

The cost is 1ms per generation — negligible.

### Token cost of retries

[CITED: https://platform.claude.com/docs/en/build-with-claude/prompt-caching]

With `cache_control: { type: 'ephemeral' }`:
- System prompt (cached): 0.30/M input tokens on read (vs 3.0/M fresh) — 90% discount
- Cache write (first call): 3.75/M (25% premium over fresh)
- TTL: 5 min default

Retry within 5 min of original call: cache_read hit on system prompt (~90% off), fresh on user messages (small — `<2KB` extra context). Estimated retry cost: ~10-15% of original call.

3-call worst case (1 original + 2 retries): ~$0.024 × (1 + 0.10 + 0.10) = ~$0.029 ≤ 0.105 × 0.024 + buffer = **acceptable** but at the edge of the 105% target.

If founder wants tighter cost control, reduce MAX_RETRIES to 1 (still 80% recovery rate per instructor data).

### Streaming UI (path b — top-level keys)

[CITED: UI-SPEC §Streaming Visual Cue]

Prompt instructs Sonnet to emit keys in fixed order:
1. `executive_summary`
2. `constitutional_pattern`
3. `systems_with_tendency`
4. `integrative_axes`
5. `bilateral_findings`
6. `therapeutic_synthesis`
7. `priority_focus`
8. `clinical_note`

Client-side detection regex per key (similar to existing parser pattern):

```ts
// Detect completed top-level key in accumulated buffer
// Matches: "key_name": "..." OR "key_name": {...} OR "key_name": [...]
// A key is "complete" when its closing bracket appears at the correct nesting depth.
const KEY_COMPLETE_RE = /"(executive_summary|constitutional_pattern|systems_with_tendency|integrative_axes|bilateral_findings|therapeutic_synthesis|priority_focus|clinical_note)"\s*:\s*/g
```

**Brittleness risk:** depth-counting brackets in a partial JSON buffer is non-trivial (string escaping, nested arrays, etc). Two safer approaches:

1. **Detect the START of the NEXT top-level key as the "PREVIOUS key complete" signal.** E.g., when `,\s*"constitutional_pattern"` appears in the buffer, mark `executive_summary` as complete. This handles depth-counting implicitly because Anthropic emits well-formed JSON.

2. **Fall back to `partial-json@0.1.7`** for buffer-level parse on every chunk. The library returns the largest valid prefix as a partial object. Bundle size: ~5KB, last updated 2024-05 (still actively used). Pure JS, edge-runtime compatible per its README.

**Recommended:** path (b1) — next-key-start detection. It's a single regex pass + zero new deps and is robust to escaping.

```ts
// apps/web/lib/anthropic/stream-parser-v2.ts (NEW) - rough sketch
const ORDERED_KEYS = ['executive_summary', 'constitutional_pattern', 'systems_with_tendency',
  'integrative_axes', 'bilateral_findings', 'therapeutic_synthesis', 'priority_focus', 'clinical_note']

export function detectCompletedKeys(buffer: string): string[] {
  const completed: string[] = []
  for (let i = 0; i < ORDERED_KEYS.length - 1; i++) {
    const nextKey = ORDERED_KEYS[i + 1]
    const nextKeyStartRe = new RegExp(`,\\s*"${nextKey}"\\s*:`)
    if (nextKeyStartRe.test(buffer)) completed.push(ORDERED_KEYS[i])
  }
  // Final key (clinical_note) marked complete when stream closes — handled by caller post-stream
  return completed
}
```

[ASSUMED] This regex-based detection works correctly because Anthropic emits well-formed JSON without inline newlines inside string values that contain literal `","key":` substrings. If founder UAT shows false positives (very unlikely given the schema), upgrade to `partial-json`.

[ANALYSIS — 30+ patterns × ~10 string fields per report × per-generation invocation]

**Option A: One mega-regex with named alternatives**

## Open landmines / risks

### LANDMINE-1: `output_config` vs `response_format` (CONTEXT mistake)

CONTEXT D-VAL1 says `response_format: { type: 'json_schema', json_schema: { name, schema } }`. The actual current API is `output_config: { format: { type: 'json_schema', schema } }`. CONTEXT was written based on stale information. The planner MUST use the SDK helper `zodOutputFormat()` which produces the correct wire format automatically.

### LANDMINE-2: Anthropic strips numeric/length constraints from JSON Schema

A zod schema like `tendency_grade: z.number().int().min(1).max(5)` will have `.min(1).max(5)` STRIPPED on the wire. The constraint still applies LOCALLY when `safeParse()` runs (the SDK does both wire-strip AND local-validate). This is correct behavior but easy to misread. Same for `priority_focus: z.array(z.string()).length(3)` — wire-stripped to `minItems: 0`, locally enforced.

**Implication:** prompt engineering must compensate. The prompt MUST tell Sonnet "tendency_grade is an integer from 1 to 5" and "priority_focus has exactly 3 items" — otherwise it'll emit `tendency_grade: 7` (Anthropic won't reject, zod will, retry triggers).

### LANDMINE-3: `claude-sonnet-4-6` model name — does NOT support response prefill

[CITED: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prefill-claudes-response — "Prefilling is not supported on Claude Mythos Preview, Claude Opus 4.7, Claude Opus 4.6, and Claude Sonnet 4.6"]

If founder ever asks "why not just prefill `{` to force JSON" — answer: Sonnet 4.6 doesn't support prefill. Structured outputs are the right path anyway.

### LANDMINE-4: streaming key-detection regex brittleness

[ASSUMED — based on Anthropic emits well-formed JSON without unusual escape sequences in pt-BR clinical prose] The `,\s*"next_key"` regex MAY false-positive if a string field contains the literal substring `","constitutional_pattern":`. Probability ≈ 0 for pt-BR clinical prose. If founder UAT shows a false positive, switch to `partial-json@0.1.7` (path a).

### LANDMINE-5: Phase 10 `report_v2_edit_diff` shape MAY be insufficient

CONTEXT D-SCH3 says shape `{ system_id: { delta_type, char_delta, levenshtein_pct } }` but UI-SPEC implies more fields might be needed (diff_summary etc per Phase 7 ClassifiedEdit). The Phase 7 `ClassifiedEdit` has 4 fields (type, diff_summary, char_delta, changed_pct). Recommendation: mirror Phase 7's `ClassifiedEdit` shape verbatim, just key it by `system_id` instead of `section_key`. Phase 10 redesigns later; this is the lowest-risk starting point.

### LANDMINE-6: PWA service worker requires explicit cache bump on rebrand

[VERIFIED: package.json has `@serwist/next@9.5.10`] Without bumping Serwist's precache version, installed PWAs may show "Aurel Iris" in the home-screen icon name for hours after deploy. Planner enumerates Serwist config (likely `apps/web/app/sw.ts`) and adds version bump as part of the rebrand task.

### LANDMINE-7: Founder may have edits in flight on legacy reports

D-LEG3 says don't reanalyze legacy. But if founder has an unsaved edit in `/leituras/:id/editar` (legacy reading) when the version-routing deploy lands, the page reload could discard their textarea state. **Mitigation:** UI-SPEC §State Persistence Contract uses `report_v2_delivered` jsonb as source of truth — same pattern for legacy means edits are server-persisted on every save. Founder edit loss risk is bounded by save frequency. Worth a heads-up but no architectural change needed.

### LANDMINE-8: Anthropic JSON Schema may reject certain zod constructs silently

[CITED: https://github.com/vercel/ai/issues/14342] If zod schema uses `.refine()` or transforms that the SDK helper can't serialize to JSON Schema, the SDK may either throw or silently drop the constraint. The `system_id` uniqueness refinement recommended in §Adaptive renderer is a good test case — if it throws when wrapped in `zodOutputFormat()`, fall back to client-side de-dupe instead.

**Mitigation:** unit test the zod schema independently of the SDK helper (run `reportV2Schema.safeParse(fixture)` directly to verify the refinement fires locally), and have a separate integration test that mocks the SDK call to confirm the wire schema is produced correctly.

### LANDMINE-9: `pnpm gen:types` requires Supabase linked project + the migrations applied

Per CONTEXT canonical_refs: `pnpm gen:types` runs `supabase gen types typescript --linked --schema public`. Requires (a) Supabase CLI authenticated, (b) project linked, (c) migrations APPLIED on the linked project. If founder runs migrations only on local-dev Supabase and not on staging/prod-linked, types file will drift. Planner adds a "regen types after migration apply" task explicitly.

### LANDMINE-10: Vercel `outputFileTracingIncludes` may not catch new prompt files

[VERIFIED: `lib/anthropic/prompts.ts` line 9 comment: "Vercel deploy: next.config.ts outputFileTracingIncludes traceia prompts/**/*.md"]

If the rewritten `system.md` is split into multiple files (e.g., `system-iris-codex.md` + `tendencies-template.md`), the existing trace pattern (`prompts/**/*.md`) covers it. But if the planner creates new prompt-related files OUTSIDE `apps/web/prompts/`, Vercel may not include them → prod 500s on first request. Recommend: keep ALL prompt files in `apps/web/prompts/`.

### LANDMINE-11: zod 4.4.1 has known incompatibilities with some `zodOutputFormat` features

[ASSUMED — based on SDK CHANGELOG 2026-02-19 fix: "zod: use v4 import path for Zod ^3.25 compatibility"] zod 4.4.1 should work but is not the latest (4.4.3 is). If `zodOutputFormat` throws unexpectedly during dev, upgrade zod to 4.4.3 first before debugging.

### LANDMINE-12: founder UAT criterion ("yes, isso lê como relatório clínico funcional") is subjective

SC-10 cannot be automated. Planner schedules a manual UAT task with explicit rubric: founder reads the regenerated Nailli report and answers yes/no to "does this read as functional, not as iridological article?" If no, the prompt needs another pass — schema doesn't change, only the system prompt copy. Plan should reserve a buffer task for prompt iteration.
