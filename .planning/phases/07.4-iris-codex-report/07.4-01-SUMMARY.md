## Decisions Made

- **Sequential int 0013/0014/0015 over 0013a/b/c**: Supabase CLI sorts strictly lexicographically and sequential ints match existing repo convention (0007..0012). Avoids ordering ambiguity if a future migration ever needs to slot between two letter-suffixed files.
- **Atomic split per concern**: schema-add → drop-legacy → new-table. If 0014 fails on push, 0013 stays applied as a valid intermediate state (new columns exist alongside the GENERATED columns); founder can re-run after diagnosis without manual recovery.
- **Backfill WHERE clause is semantic, not temporal**: `report_generated IS NOT NULL` — only readings that actually produced legacy Phase 7 output get the '1.0' tag. Temporal cutoffs (e.g., `created_at < deploy_timestamp`) would be brittle across staging/prod and would mis-tag any future reading that for some reason re-runs the legacy path.
- **report_version DEFAULT '2.0'** (forward) with explicit backfill flipping legacy to '1.0' (reverse): new readings need zero application code change to be marked correctly; the DEFAULT does the work.
- **reading_addons RLS V1: SELECT + INSERT only** — append-only by design (a generated add-on report is an artifact; regenerating creates a new row). UPDATE/DELETE policies deferred to V1.1 when regeneration semantics are defined.
- **reading_addons table created empty in V1** — schema + types exist so V1.1 plans don't have to ship migrations + features in the same wave. Substrate decoupled from feature.
- **Linked-project gate is founder-owned, not automated** (Q4 RESOLVED 2026-05-13): `pnpm supabase db push` runs against whichever project `supabase link` last selected. Plan checkpoint requires founder to visually confirm `supabase status` output before push. Avoids the risk of an autonomous agent pushing to prod when staging was intended.
