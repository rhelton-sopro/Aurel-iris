## Decisions Made

- **§11 Afirmações deferred to Plan 12 as separate optional toggle (NOT placed in the §1..§14 numbered sequence):** DC-1 originally listed Afirmações as §11. Plan 11 keeps the 14 always-emitted sections as a contiguous 1..14 block to preserve parser monotonia (the strictest defense against Sonnet drift). Afirmações becomes a conditional section in Plan 12 implemented alongside the UI toggle. This is a Rule-4-equivalent scope adjustment that was front-loaded into the PLAN.md canonical_section_keys block — not an in-execution deviation.
- **Anchor-rate audit dual-pathed instead of dropped:** Plan critical_constraints suggested dropping anchor-rate logic if it depended on the 5-section subset. Discovered during Task 4 that 5 downstream consumers (save-action gate, AuditBanner, AnalysisHero, ReparseReportButton, scripts/reparse-reading.mjs) actively read `low_anchor_rate` and `anchor_rate_pct`. Dropping the audit fields would break the save-action gate's CR-05 contract for legacy 1.0 readings (which still contain inline `[ancorado em features.x]` markers per the original D-A1 contract). Solution: dual-path the audit so legacy reports keep semantic scanning while new reports get deterministic passing values — both paths produce the same AuditMetadata shape, so downstream consumers compile and run unchanged.
- **EditorAccordion updated structurally (new keys + new titles), UI not redesigned:** Plan 12 will rebuild for §11 toggle + §14 warm-voice rendering. Plan 11 keeps the legacy accordion structurally rendering the new keys so the app compiles and legacy 1.0 readings can be regenerated end-to-end (resolves D-DEF-09-05). Editing the new 14 sections via the accordion works but the visual treatment is unchanged from the Phase 7 design.
- **system.md does NOT include the LGPD encerramento literal:** server-side append preserved per D-P3. Prompt explicitly instructs Sonnet "Não emita ENCERRAMENTO ou DISCLAIMER após §14 — o servidor anexa esse texto LGPD automaticamente."
