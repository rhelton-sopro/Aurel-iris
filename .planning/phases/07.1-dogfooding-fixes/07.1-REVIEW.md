## Warnings

### WR-01: `compute_asymmetry` lacuna asymmetry condition uses `not left_findings` instead of `not left_has_lacuna` (mirror on the other branch)

**File:** `vision-service/pipeline/features.py:539-542`
**Issue:** Lines 537-538 compute `right_has_lacuna` and `left_has_lacuna`, but the asymmetry condition on line 539 reads `if right_has_lacuna and not left_findings` — it tests the *entire* findings list rather than the lacuna-specific predicate. Mirror bug on line 541 (`not right_findings`). A left eye that has *some* finding in sector h that is NOT a lacuna (e.g., `pigmentacao` or `cripta`) would silently mask a unilateral lacuna asymmetry: `not left_findings` becomes False even though there is no lacuna on the left side. The variable `left_has_lacuna` is computed and then never used, which is a strong hint the intended predicate was lost in a refactor. The current test (`test_compute_asymmetry_lacuna_unilateral_right`) doesn't surface this because it leaves the contralateral sector empty.
**Fix:**
```python
if right_has_lacuna and not left_has_lacuna:
    notes.append(f"lacuna_unilateral_setor_{h}_direito")
elif left_has_lacuna and not right_has_lacuna:
    notes.append(f"lacuna_unilateral_setor_{h}_esquerdo")
```
Add a regression test where left_block has a non-lacuna finding (e.g., `pigmentacao`) in the same sector as right's lacuna, asserting `lacuna_unilateral_setor_h_direito` is still emitted.

### WR-02: `_classify_constitution` Branch 1 (`neurogenica`) requires `interpretation == "densa"` but the fiber-density quartile uses a `<` comparator everywhere else — boundary inconsistency

**File:** `vision-service/pipeline/features.py:302-305` (with `_compute_fiber_density:246-253`)
**Issue:** `_compute_fiber_density` uses `score < FIBER_DENSITY_BANDS[2]` (0.85) to fall into `media-densa` and everything `>= 0.85` lands in `densa`. The constitution heuristic Branch 1 then requires `interpretation == "densa"` for neurogenica. This is internally consistent for current bands, but Branch 3's biliar split (`if interpretation == "densa"`) on line 320 has the same dependency. If a downstream tweak changes the band labels (e.g., introducing `muito-densa` or renaming `densa` → `alta`), Branch 1 silently degrades to linfatica and Branch 3 silently degrades to mista_biliar with no test catching the regression. The labels are de-facto enum values but are not typed as such. The `KMEANS_K` / `IRIS_COLOR_LABELS` constants in the same file are exposed for tuning, but `densa`/`media-densa`/`media`/`esparsa` are not.
**Fix:** Lift the four labels into a named constant (e.g., `FIBER_DENSITY_LABELS: tuple[str, str, str, str] = ("esparsa", "media", "media-densa", "densa")`) and reference `FIBER_DENSITY_LABELS[3]` in both `_compute_fiber_density` and `_classify_constitution` so a future rename hits a single source of truth. Add a unit test asserting that `_compute_fiber_density(uniform_high_gradient_image)["interpretation"] == FIBER_DENSITY_LABELS[3]`.

### WR-03: `recalibrate-centroids.mjs` assumes Sharp returns 3 or 4 channels — grayscale images cause index-out-of-bounds NaN propagation

**File:** `apps/web/scripts/recalibrate-centroids.mjs:134-148`
**Issue:** `info.channels` from Sharp can be `1` (grayscale), `2` (grayscale+alpha), `3` (RGB), or `4` (RGBA). The loop on line 135 uses `channels` as the stride, but `pixels[i + 1]` and `pixels[i + 2]` are accessed unconditionally. For a `channels=1` image, `pixels[i + 1]` reads the *next* gray pixel and `pixels[i + 2]` reads the one after that, silently treating consecutive gray pixels as R/G/B. The result is a meaningless centroid that gets averaged into the proposal. Worse, when the iteration walks past the buffer end on the final stride, `pixels[i + 1]` and `pixels[i + 2]` return `undefined`, `undefined / 255` is `NaN`, every subsequent LAB conversion produces `NaN`, and the printed proposal row shows `NaN` LAB values that look like a successful proposal at a glance.
**Fix:** Guard against non-RGB channel counts early in `downloadAndCentroid`:
```javascript
if (channels !== 3 && channels !== 4) {
  throw new Error(`unsupported channel count ${channels} for ${storagePath} — convert to RGB first`)
}
```
Also, after the loop, guard `n === 0` (already present) AND verify the running sums are finite before returning. Sharp's `.ensureAlpha()` or `.removeAlpha()` could be chained on the `extract()` call to normalize input.

### WR-04: `extractForbiddenHits` 30-char lookback can be insufficient and reaches across sentence boundaries

**File:** `apps/web/lib/anthropic/audit.ts:98, 126-128`
**Issue:** `NEG_LOOKBACK_CHARS = 30` covers "não substitui " (16 chars) plus comfortable buffer for the shortest verbs, but a real LGPD-correct sentence Sonnet can emit is "Esta análise **não** é, em hipótese alguma, um diagnóstico médico" — here "diagnóstico" sits well over 30 chars from "não". The window misses the negative context and a hit is recorded. Conversely, the lookback is sentence-blind by design (test `C2 regression: "não" em outra cláusula NÃO mascara hit subsequente` exists), but the boundary is set by character count rather than sentence delimiter, so a sentence-blind regex can still false-skip if the prior sentence ends in `não é`. Example: "Não é. Sugere diagnóstico" — `"Não é. Sugere "` is 14 chars; with the window at 30, the preceding slice captures `"Não é. Sugere "`. NEG_CONTEXT_RE is anchored `\s*$`, so it must match "não é" *followed by whitespace through end*; ". Sugere " breaks the anchor. The test on line 318-324 confirms this works. So this branch is OK — the *real* risk is only the first case (long parenthetical between "não" and the forbidden term).
**Fix:** Either bump `NEG_LOOKBACK_CHARS` to 60-80, or — better — split the section text on `SENTENCE_SPLIT_RE` first and run `extractForbiddenHits` per sentence with the lookback bounded by the sentence start. The latter aligns with `countAnchoredSentences`'s existing splitter and makes the contract explicit. Add a fixture: `"Não, em hipótese alguma, esta análise constitui um diagnóstico médico."` — expect 0 hits (currently emits 1).

### IN-04: `sectoral_pigments` docstring says intensity formula is `|delta_a + delta_b|` for laranja but code computes `|delta_a| + |delta_b| - 8`

**File:** `vision-service/pipeline/sectoral_pigments.py:25` (docstring) vs `:120` (code)
**Issue:** The module docstring at line 25 says intensity for laranja is "|delta_a + delta_b|", but the implementation at line 120 computes `abs(dA) + abs(dB) - 8`. The `-8` subtracts the laranja threshold (so intensity is "magnitude above threshold"), and the use of `abs(dA) + abs(dB)` rather than `abs(dA + dB)` differs when signs cancel (here both deltas are guaranteed positive, so the values coincide, but the docstring is still misleading).
**Fix:** Update docstring to match: `"Intensity for laranja: (|delta_a| + |delta_b|) - 8 (threshold-adjusted magnitude)"`.
