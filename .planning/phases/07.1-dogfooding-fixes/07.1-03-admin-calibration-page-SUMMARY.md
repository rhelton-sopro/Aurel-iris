## Decisões de execução

### Decisão founder confirmadas pré-execute
- **FOUNDER_EMAIL = rhelton@gmail.com** (env var em `.env.local` + Vercel)
- **RLS strategy:** middleware é gate primário (TS); RLS hardcoded com email
  literal como defense-in-depth. Trade-off: trocar founder requer nova migration.
  Aceitável porque founder é singular por design Phase 7.1.
- **Migration:** 0009 (último era 0008_readings_report_raw_text.sql).

### Decisões inline durante execução

- **Photo download = JSON of signed URLs (não zip server-side)** — escolha
  default do PLAN. Avoid Vercel function memory issues com 6×2-3MB photos
  zipped. Browser baixa cada uma separately com filename correto.
- **Service-role para list + detail + photos route** — admin tool por design
  ignora RLS de readings/reading_images (que exige `auth.uid() = therapist_id`).
  Founder gate em 3 camadas garante segurança.
- **Re-saving annotation flips reviewed=false** — semântica explícita: founder
  deve re-marcar como revisada após editar. Evita "anotação editada mas ainda
  marcada revisada" como estado silencioso.

## Deviations

### Rule 1 — `/404` rewrite → status 404 response (T2)

**PLAN's interface code:**
```ts
return NextResponse.rewrite(new URL('/404', request.url))
```

**Problema:** `/404` route não existe no App Router (verificado via
`find apps/web/app -name "not-found*" -o -name "404*"` → empty). O rewrite
falharia silenciosamente com Next.js renderizando uma página vazia ou erro.

**Fix:** `return new NextResponse(null, { status: 404 })`. Defense-in-depth
preservado via `app/admin/layout.tsx` que chama `notFound()` (renderiza Next's
built-in not-found page com styling apropriado). Resultado UX: middleware
bloqueia raw request → status 404; layout chamado se middleware furar →
not-found page properly styled.
