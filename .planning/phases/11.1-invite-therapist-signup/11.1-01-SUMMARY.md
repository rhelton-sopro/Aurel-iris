# Phase 11.1 Plan 01: Migration 0033 + types regen Summary

**One-liner:** `therapist_invites` table (token uuid + 7d TTL + RLS-locked) + `clients_therapist_email_unique` constraint aplicados via migration 0033; types/database.ts regenerada — Wave 2 (11.1-02) desbloqueado.

## What Was Built

### Migration `0033_therapist_invites_and_client_email_unique.sql`

**Tabela `therapist_invites`:**
- `token uuid` PK default `gen_random_uuid()` — forma da URL `/convite-terapeuta/{token}`
- `email text` (originalmente `citext`, ver Deviations) NOT NULL — email do terapeuta convidado
- `invited_by uuid` NOT NULL FK `profiles(id)` ON DELETE CASCADE
- `created_at timestamptz` NOT NULL default `now()`
- `expires_at timestamptz` NOT NULL default `(now() + interval '7 days')` — **D-TTL**
- `used_at timestamptz` NULL — idempotência (token 1× uso)
- `used_by_user_id uuid` NULL FK `auth.users(id)` ON DELETE SET NULL

**3 Indexes:**
- `therapist_invites_email_idx` em `email` (lookup p/ duplicate detection)
- `therapist_invites_token_active_idx` em `(token, expires_at, used_at)` WHERE `used_at IS NULL` (validação rápida no GET)
- `therapist_invites_invited_by_idx` em `invited_by` (futura UI de convites enviados)

**RLS:** Habilitada SEM policies para `authenticated`/`anon` — bloqueio total client-side. Service role bypass naturalmente. Defense-in-depth contra leak de tokens.

**8 COMMENTs** documentando D-DUPE, D-TTL, D-CLIENT, D-OTP — coluna por coluna.

**UNIQUE constraint em clients (D-CLIENT):**
- `clients_therapist_email_unique unique (therapist_id, email)` — per terapeuta, NÃO global
- Resolve memory tech debt `project_clients_unique_email_tech_debt`

### `apps/web/types/database.ts` regenerada

- `Database['public']['Tables']['therapist_invites']` com `Row` + `Insert` + `Update` + `Relationships`
- Todas as 7 colunas tipadas (uuid → string, timestamptz → string, FK nullable corretos)
- FK `therapist_invites_invited_by_fkey` → `profiles(id)` reconhecida pelo gen:types
