# Fase 11.1 — Invite terapeuta via signup form (INSERTED 2026-05-26)

**Trigger:** Bug bloqueador descoberto durante smoke E2E da Fase 9 (09-05 Task 2). Founder gerou invite link em `/admin/terapeutas` mas terapeuta caiu em `/login` ao invés de página de cadastro com email pré-preenchido.

**Status original (Fase 11 11-01):** "Hand-held protocol — founder controla quando e como o terapeuta recebe — sistema NÃO envia e-mail automático" via `service.auth.admin.generateLink({ type: 'invite', redirectTo: /dashboard })`. **Não funciona** por 2 motivos.

## Diagnóstico do bug

**Bug 1 (técnico): PKCE code não é trocado por sessão**

`apps/web/app/actions/admin-therapists.ts:58` define `redirectTo = ${siteUrl}/dashboard`. Mas o Supabase client roda em modo PKCE (default do `@supabase/ssr`). Fluxo real:
1. Founder gera link → `supabase.auth.admin.generateLink({ type: 'invite' })` retorna URL contendo token Supabase
2. Founder copia URL e manda via WhatsApp
3. Terapeuta clica → Supabase Auth `/verify` confirma user → redireciona para `${siteUrl}/dashboard?code=xxx`
4. `/dashboard` é rota Next.js comum, NÃO troca code por sessão
5. Middleware vê `/dashboard` sem cookie de sessão → redireciona pra `/login`

Existe handler em `apps/web/app/api/auth/callback/route.ts` que faz `exchangeCodeForSession(code)` e redireciona pra `/dashboard`. Esse é o `redirectTo` técnicamente correto.

**Bug 2 (UX/design): falta cadastro de dados profissionais**

Expectativa founder: terapeuta clica link → cai em **signup form com email pré-preenchido** → preenche nome + WhatsApp + specialties + TOS → ativa via OTP → /dashboard.

Comportamento atual (com Bug 1 corrigido seria): terapeuta clica link → logado direto sem dados profissionais → middleware redireciona pra `/perfil/completar` (sem email, pede só nome + WhatsApp + specialties + TOS via UPDATE profile).

Funcionalmente entrega o mesmo profile no final, mas o caminho UX é diferente. Founder prefere o flow A (signup form pré-preenchido) porque:
- Match com `/signup` existente (uniformidade)
- Founder pode revisar email no campo antes de submeter (defensa contra digitação errada)
- Captura TODOS os dados num único form, não em rota intermediária

## Requirement adicional capturado durante discussion

**UNIQUE constraint em clients.email per terapeuta:**
- Memory `project_clients_unique_email_tech_debt` documentava esse tech debt como deferred
- Founder solicitou nesta fase: "e tb não deixar ter mais de um cadastro de terapeutas e tb de clientes por email"
- Decisão D-CLIENT: `UNIQUE(therapist_id, email) ON clients` — per terapeuta, não global
- Para terapeutas: `auth.users.email` já é UNIQUE nativo do Supabase + check explícito em `inviteTherapistAction` antes de gerar token

## Decisões locked

### D-DUPE — Email já cadastrado: bloqueia convite
Se founder tenta convidar email já existente em `auth.users`, retorna erro `"E-mail já cadastrado como terapeuta neste sistema."` sem gerar token.

**Implicação:**
- `inviteTherapistAction` faz `service.auth.admin.listUsers({ filter: "email.eq.${email}" })` (ou `getUserByEmail` se disponível) ANTES de gerar token
- Toast no `InviteTherapistForm` mostra erro amigável
- Sem fallback magic-link nem "re-entry" — limpo: ou tá cadastrado e usa /login, ou é novo e ganha invite via /convite-terapeuta/[token]

### D-TTL — Token expira em 7 dias
Coluna `expires_at = created_at + interval '7 days'` no DB. Lookup em `/convite-terapeuta/[token]` checa `expires_at > now()`. Se expirado → 404 com mensagem clara.

**Implicação:**
- Default tipicamente 1h é curto para hand-held WhatsApp (founder pode mandar link e terapeuta abrir 2 dias depois)
- 30 dias seria largo demais (mais janela de vazamento)
- 7 dias é meio-termo razoável; pode ser revisto se reclamação

### D-OTP — OTP obrigatório no submit do form
Form submit chama `signInWithOtp({ email, options: { data: meta, shouldCreateUser: true } })` → step 'code' → `verifyOtp({ email, token, type: 'email' })` → sessão. Confirma posse do email + previne convite roubado.

**Implicação:**
- UX matches `/signup` existente (founder + terapeutas já cadastrados conhecem o flow)
- Tempo extra ~2min do terapeuta, mas é overhead aceitável para B2B beta
- Token de convite é "permissão de cadastrar com este email", não "sessão automática"

### D-ROUTE — Rota dedicada `/convite-terapeuta/[token]`
NÃO reusa `/signup?token=xxx`. Rota nova segue padrão de `/convite/[token]` (cliente) que já existe na app — mantém analogia.

**Implicação:**
- Server component faz lookup de token + valida + passa email pra client form
- Form é client component novo `TherapistInviteSignupForm` (não compartilha código com `SignupPage` pra evitar prop hell condicional)
- Middleware reconhece `/convite-terapeuta/` como prefix público (igual `/convite/` já reconhece)

### D-CLIENT — UNIQUE(therapist_id, email) em clients
Migration 0033 adiciona constraint. `createClientAction` (e similar) trata violation com mensagem amigável: `"Cliente com este e-mail já cadastrado em sua lista."` Não impede que terapeuta B tenha o mesmo email do terapeuta A.

**Implicação:**
- Resolve memory tech debt `project_clients_unique_email_tech_debt`
- Backfill: NÃO há clientes duplicados em prod (founder confirmou via discussion); migration sem ON CONFLICT
- Se vier a ter dup em prod ANTES desta migration, query SQL identifica + delete manual antes do push
