# Code Review — Fase 11.1 (Invite terapeuta via signup form)

## Summary

Fase 11.1 introduz um novo auth boundary de alto risco: tokens de convite de terapeutas com 7 dias de TTL, uma rota RSC publica, um form client com OTP, e uma server action de mark-used. A implementação tem design geral sólido — UUID v4 entropy, email display-only, UPDATE idempotente com `.is('used_at', null)`, RLS bloqueio total client-side, founder gate defense-in-depth.

Foram encontrados **2 BLOCKERS críticos**, **1 HIGH**, **1 MEDIUM** e **2 INFO**.

## Findings

### CRITICAL — Block before merge

#### CR-01: Token UUID exposto em log de produção
**File:** `apps/web/app/actions/admin-therapists.ts:107-113`

`console.log` de audit imprime `token: invite.token` — o UUID completo do convite gerado. Em produção esse log é capturado pelo Vercel (dashboard Logs tab, também acessível via `vercel logs`). Qualquer pessoa com acesso ao Vercel dashboard ou a um export de logs consegue extrair o token e navegar para `/convite-terapeuta/{token}` antes do terapeuta alvo, completando o signup com o email da vítima.

O token UUID é a única credencial que autentica o convite. O OTP subsequente confirma posse do email — MAS o invasor pode usar o próprio email do token (que também está no log como `targetEmail: email`). Resultado: `token + targetEmail` no log = convite completamente utilizável por terceiros.

**Fix:** Logar apenas prefixo (suficiente pra debug correlation):

```typescript
console.log('[admin-therapists] INVITE_TOKEN_GENERATED', {
  targetEmail: email,
  tokenPrefix: invite.token.slice(0, 8), // debug correlation only — never full token
  userStatus: 'new_invited',
  by: user.email,
  at: new Date().toISOString(),
})
```

#### CR-02: D-DUPE check silenciosamente falha após 1000 usuários em auth.users
**File:** `apps/web/app/actions/admin-therapists.ts:68`

`service.auth.admin.listUsers({ perPage: 1000 })` retorna no máximo 1000 registros. Quando `auth.users` tiver 1001+ registros, a chamada retorna somente os primeiros 1000 sem erro e sem indicação de truncamento. O filtro client-side na linha 75 passa a operar em lista incompleta, tornando possível criar um segundo registro pro mesmo email que está na "segunda página".

Falha silenciosa: o check retorna `false` (não existe), não um erro. O founder não receberá aviso; o convite será gerado e um segundo auth.user será criado pro mesmo email (violando a unicidade esperada).

**Fix:** Usar `getUserByEmail` (Supabase Admin SDK >= 2.38):

```typescript
const { data: existingUser } = await service.auth.admin.getUserByEmail(email)
if (existingUser?.user) {
  return { ok: false, error: 'E-mail já cadastrado como terapeuta neste sistema.' }
}
```

Fallback se `getUserByEmail` não disponível: usar filter param ou verificar `total > 1000` e abortar.

### HIGH — Fix before merge OR document risk acceptance

#### WR-01: updateClientAction não trata 23505 clients_therapist_email_unique
**File:** `apps/web/app/actions/clients.ts:111`

`createClientAction` (linha 67) trata violação `clients_therapist_email_unique` com mensagem amigável. `updateClientAction` (linha 111) tem apenas `return { error: error.message }` — retorna erro raw do Postgres ao cliente se o terapeuta atualizar um cliente pra email que já existe em outro registro seu.

A constraint `UNIQUE(therapist_id, email)` é violável em UPDATE também (terapeuta A tem cliente X com email foo@bar.com e cliente Y sem email; ao adicionar email foo@bar.com a Y, dispara 23505). Usuário recebe string de erro de banco crua em vez da mensagem amigável.

**Fix:** Aplicar mesmo tratamento de `createClientAction`:

```typescript
if (error) {
  if (
    error.code === '23505' &&
    error.message.includes('clients_therapist_email_unique')
  ) {
    return { error: 'Cliente com este e-mail já cadastrado em sua lista.' }
  }
  return { error: error.message }
}
```

### MEDIUM — Fix in follow-up

#### WR-02: Diferenciação "token usado" vs "não existe" vaza estado de tokens passados
**File:** `apps/web/app/convite-terapeuta/[token]/page.tsx:30-44`

Quando `invite.used_at` é não-nulo, page renderiza mensagem específica: "Este convite já foi usado." Quando token não existe, `notFound()` → 404. Cria oráculo: atacante com UUIDs de tokens passados (ex: via log leaked do CR-01) pode confirmar quais foram "usados" vs "nunca existiram".

Risco concreto baixo neste modelo de dados (informação "foi usado" não dá acesso a nada). Mas leak de informação interna sobre tokens históricos sem adicionar UX necessária. Mesma análise pra "expirado".

**Fix mais seguro:** colapsar estados inválidos em 404:

```typescript
if (error || !invite || invite.used_at || new Date(invite.expires_at) < new Date()) {
  notFound()
}
```

**Alternativa:** manter mensagens + documentar como trade-off consciente no CONTEXT.md.

### LOW / Nitpick — Defer or skip

#### IN-01: inviteTherapistAction não chama revalidatePath após INSERT
**File:** `apps/web/app/actions/admin-therapists.ts:114-120`

Happy path retorna `{ ok: true, ... }` sem `revalidatePath('/admin/terapeutas')`. Se futuramente houver lista de "convites enviados" nessa página (o index `therapist_invites_invited_by_idx` sugere caso de uso antecipado), cache não invalida.

`deleteTherapistAction` faz isso na linha 245. Inconsistência.

#### IN-02: import 'server-only' ausente em clients.ts
`therapist-invites.ts` e `admin-therapists.ts` importam `import 'server-only'` como defesa de segunda camada. `clients.ts` tem `'use server'` mas não tem `'server-only'`. Drift de padrão.

São complementares (não redundantes): `'use server'` marca como Server Actions boundary; `server-only` previne import acidental em Client Components (bundler-level).

## Strengths

1. **Email display-only real** (`div > strong`, não `input disabled`) — `signInWithOtp` usa prop `tokenEmail` do server, nunca state DOM mutável. T-11.1-03-02 genuinamente mitigado.
2. **UPDATE idempotente** (`.is('used_at', null)`) — race de duplo clique resolvida na camada DB.
3. **UUID regex antes do DB query** em `page.tsx:14` — `notFound()` imediato pra path não-UUID. Previne path scanning.
4. **RLS bloqueio total sem policies** — tabela `therapist_invites` não acessível por nenhum `authenticated` ou `anon` role. Só service role. Defense-in-depth real.
5. **`use server` export hygiene** em `therapist-invites.ts` — apenas async function exportada.
6. **Middleware bail-out antes do updateSession** — `/convite-terapeuta/` retorna `NextResponse.next()` direto. Consistente com `/convite/`.
7. **FK `invited_by → profiles ON DELETE CASCADE`** — sem orphan tokens.

## Cross-cutting observations

- **MEMORY `feedback_supabase_rls_no_auth_users`**: Nenhum arquivo faz query em `auth.users` via Supabase client. `getUserById`/`listUsers` via Admin API (não SQL).
- **MEMORY `feedback_use_server_export_hygiene`**: `therapist-invites.ts` + `admin-therapists.ts` OK. `clients.ts` exporta `ClientFormState` type — TS types são erased no bundle; aceitável.
- **MEMORY `feedback_iris_codex_seven_rules` / LGPD**: zero vocab proibido nos arquivos revisados.
- **Token via WhatsApp**: design intencional ("hand-held protocol") significa que token trafega pelo WhatsApp de qualquer forma. **CR-01 (token no log) é vetor adicional e diferente** — logs têm acesso mais amplo do que canal WhatsApp (que ao menos é E2E encrypted). Ambos canais devem ser considerados.
